# Rift MCP System

## Purpose

Rift MCP is RiftOS's local model-capability boundary. It exposes a finite set of workspace and shell tools while keeping schemas, permissions, auditing and execution authority on-device.

## Source ownership

Native core:
- `RiftMcpRuntime.kt` — process-wide singleton wiring.
- `RiftMcpServer.kt` — MCP JSON-RPC methods and result framing.
- `RiftToolHost.kt` — canonical tool registry, schemas, permissions and audit.
- `RiftToolSandbox.kt` — workspace-only implementation and Code Mode.
- `RiftMcpActivity.kt` — local permission/relay/status UI.

Supporting subsystems:
- `RiftProjectExporter.kt` — deterministic source export.
- `RiftMcpRelayClient.kt` / `RiftRelaySettings.kt` — optional outbound remote transport.
- `RiftShellBridge.kt` — narrow bridge for `rift_shell_exec` into existing RiftShell.
- `src/riftmcp-system.js` — launcher/start-menu entry.
- browser MCP compatibility assets — one optional client transport.

## Canonical flow

```text
client transport
  -> RiftMcpServer
  -> RiftToolHost
      -> permission + schema + bounded audit
      -> RiftToolSandbox OR RiftShellBridge
  -> result
```

The server and tool host are shared by local browser compatibility and the optional secure relay. Transport never receives extra filesystem authority.

## Tool catalog

The authoritative catalog is generated by `RiftToolHost.tools()`. `RiftToolHost.manifest()` returns names, count and SHA-256. `rift_info` embeds the same manifest so stale clients can be diagnosed even if they cached an older tool list.

The current catalog contains 18 tools: shell exec; info/stat/hash/list/read/write/mkdir/remove/move/copy/archive/extract; audit/scan; project export; read-only `rift_workspace_diff`; and `rift_workspace_exec`.

## Permission model

Read defaults enabled; write defaults disabled. `rift_workspace_exec` is read-gated and additionally write-gated when any operation mutates. `rift_shell_exec` requires both read and write permission because shell commands can mutate outside MCP's workspace-only filesystem surface through RiftShell's own authority.

## Filesystem boundary

Normal MCP filesystem tools are hard-scoped to `filesDir/riftfs/workspace`. They cannot address `/home`, downloads, documents, SAF mounts, system roots or arbitrary Android storage. The shell tool is intentionally a different capability and routes to RiftShell, not `RiftToolSandbox`.

## Failure signatures

- Native UI reports 17 but client reports fewer -> stale client action/schema scan; compare `rift_info.mcpManifest`.
- Read works/write denied -> local write grant disabled.
- Only one tool fails -> tool mapping/argument/sandbox implementation.
- All relay calls fail but browser-local works -> relay transport/settings/service.
- Browser-local fails but relay works -> browser compatibility/bridge.

## Fix map

JSON-RPC framing/idempotency -> MCP server.
Tool registration/schema/grants/audit -> tool host.
Workspace operation semantics/transactions -> sandbox.
Remote connection -> relay client/service.
Transactional mutation rollback -> `RiftToolSandbox` copy-on-write batch handling.

## Validation

Run repository transport validation and compare `RiftToolHost.tools()` count with `manifest().count`. Test through both available transports when changing shared MCP behavior. Do not use transport-specific workarounds to bypass device-side grants.
